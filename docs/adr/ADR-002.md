# ADR-002 双层持久化：SQLite WAL 热层 + 冷层原子写 + 轮换恢复快照

**状态**：Accepted

**日期**：2026-08-10

## 背景/Context

SC-003 要求保存中断文件损坏率 0；FR-012/013 与 SC-004 要求崩溃恢复窗口 ≤5s；高频绘制期磁盘写入次数 ≤编辑事件数的 1%（SC-006）。单一存储方案无法同时满足低延迟草稿吞吐、最终文件原子性与崩溃恢复。

## 决策/Decision

采用"热层 + 冷层 + 恢复快照"的三层持久化（research.md R2/R5/R6、plan.md D2/D5、data-model.md）：

1. **热层：SQLite WAL**（rusqlite bundled）承载全部热层数据：`drafts`（草稿）、`workspaces`、`file_index`、`file_meta`。PRAGMA 基线：`journal_mode=WAL; busy_timeout=5000; foreign_keys=ON; synchronous=NORMAL`；草稿关键提交路径可用独立连接 `synchronous=FULL`。
2. **冷层：标准 `.excalidraw` 文件原子写**——六步流水线：同卷 `.tmp` 创建 → 写入 + `sync_all()`（fsync）→ 重读反序列化校验 JSON 完整性 → `std::fs::rename` 原子替换 → 父目录 fsync → 异常路径清理 `.tmp`。冷层文件是最终事实来源，即使 WAL 极端断电丢失最后 0.1s 提交，用户文件依然完好。
3. **恢复快照：会话锁 + 多版本轮换**——应用数据目录 `session.lock`（含 PID 与启动时间戳，正常退出清理）判定异常退出；每文档 3–5 份 Ring Buffer 轮换快照 `recovery/<doc-hash>/recovery-NNN.json`（含 documentId、originalPath、baseFileHash、savedAt、appVersion、完整 scene）；启动时以 `savedAt > cold mtime` 和 scene 差异识别普通未保存草稿，以 `baseFileHash` 与冷层 hash 差异识别外部替换；冷层缺失或不可读时保留候选并引导另存。

数据模型层强制以下不变量（data-model.md §4）：

1. 任何状态下冷层文件只能经原子写流水线修改（禁止直接覆盖句柄写入）。
2. `Conflicted` 状态下禁止一切自动 checkpoint，直至用户决策（FR-019）。
3. `Checkpointed → Clean` 转换必须与 `drafts.is_dirty=0`、`file_index` hash 更新在同一事务语义内完成。
4. 应用退出路径必须阻塞等待所有非 `Clean`/`Orphaned` 文档完成 checkpoint 或显式放弃。

## 后果/Consequences

**积极**：

- 冷层 rename 原子性在 APFS/ext4/btrfs 下保证文件要么旧完整、要么新完整，满足 SC-003。
- 草稿高频写入走 WAL 追加，满足 300ms 防抖吞吐与 SC-006 削峰要求。
- 多版本轮换对冲快照自身损坏，满足 SC-004（≤5s 恢复窗口）。

**消极**：

- 两套存储位置增加运维与实现复杂度（迁移、路径校验、事务语义边界）。
- WAL 极端断电可能丢失最后约 0.1s 草稿提交（已由冷层事实来源兜底，属接受范围）。
- 恢复快照占用磁盘，轮换与清理需要生命周期管理。

## 备选方案/Alternatives

- **单快照**：快照损坏即全失，不满足 SC-004。
- **事件日志重放**：实现复杂度高；Excalidraw scene 全量体量可控，无必要。
- **直接覆盖写**：存在半写损坏窗口（tyrchen/excaliapp 30s 全量覆盖模式），违反 SC-003。
- **写前备份副本**：双倍 IO 且不解决写入中断原子性。
