## 1. 计划目标与执行约束

### 1.1 目标

本计划将 PRD 中的产品目标拆成可交付的技术切片、接口契约、测试夹具和发布门禁，形成从空白 Tauri 脚手架到跨平台 MVP/Beta 的可追踪路径。

实施完成时，系统应能够：

- 在支持矩阵中的 macOS 与 Linux 环境离线创建、打开、编辑、保存、恢复和导出标准 `.excalidraw` 文件。
- 通过 SQLite 热层保存可恢复草稿，通过冷层原子替换保存用户文件。
- 在保存前检测外部变化，在冲突时阻止静默覆盖。
- 通过最小权限、非空 CSP、Rust 侧输入和路径验证建立 Tauri 安全边界。
- 用自动化测试、故障注入、性能夹具和真实平台冒烟测试证明 PRD 门槛。

### 1.2 已确认执行决策

| 决策 | 本计划约束 | 影响 |
| --- | --- | --- |
| 平台范围 | 只规划 macOS + Linux；Windows 不进入当前交付和测试矩阵。 | 不实现 Windows 专用文件监听、签名、安装包和 UI 兼容逻辑；未来扩展另立计划。 |
| 热层数据库 | 第一实现使用 SQLite（优先 WAL 配置），包含迁移、事务和故障测试。 | 先建立一个可运行的存储路径，不并行维护两个实现。 |
| redb | 不是当前依赖或实现目标。仅当 SQLite 在针对性修复后仍无法通过已批准门槛，才提交 ADR 评估迁移。 | 避免提前引入双存储抽象和迁移成本；保留可替换的仓储接口。 |
| 其他 ADR | 不在本次计划前置定稿。SDK 版本、Linux 矩阵、保存阈值、字体、分发格式等在对应阶段用证据决策。 | 计划提供默认候选与退出条件，不把猜测写成事实。 |

### 1.3 不在本计划内

- Windows 支持、Windows 构建、Windows 文件关联与 Windows 发布。
- 实时协作、账号、云同步、插件市场、自动 Scene 合并。
- 自动更新、内容寻址外置图片、完整版本历史和多工作区搜索。
- 未经许可证、渲染和导出验证的 CJK 手绘字体合并。
- 以研究文档中的包体积、内存、启动或 IO 数字代替本仓库实测。

## 2. 规格追踪与完成定义

### 2.1 需求追踪规则

每个实施任务必须在任务描述中引用至少一个 PRD ID（例如 `FR-PS-004`、`US-004`、`NFR-R-001`）。每个 PR 必须说明：

1. 变更覆盖的需求 ID。
2. 变更的接口、状态或数据迁移影响。
3. 新增或更新的测试夹具。
4. 尚未验证的风险和后续 ADR（如有）。

### 2.2 Definition of Ready（任务开始前）

任务只有在以下条件满足后才能进入实现：

- 目标行为和验收条件可从 PRD 或本计划定位。
- 输入、输出、错误状态和权限边界已描述。
- 依赖任务和迁移影响已列出。
- 测试层级已确定；若需要真实平台或故障注入，已指定验证环境。
- 不会引入 Windows 范围或未批准的产品功能。

### 2.3 Definition of Done（任务完成时）

- 代码、契约、迁移和文档与任务范围一致。
- 相关单元/集成/E2E/平台测试已运行，或明确记录无法运行的外部条件。
- 无新增未分类的错误吞噬、路径越权、秘密泄露或假“已保存”状态。
- PRD ID、测试结果、已知限制和回滚方式写入变更说明。

### 2.4 产品级 MVP 完成定义

Phase 1 和 Phase 2 是内部 Alpha 增量，不得称为产品级 MVP。只有 Phase 3 同时满足以下条件，才能将版本标记为跨平台 MVP/Beta：

- PRD 中所有 Must 用户故事通过。
- 所选 macOS/Linux 矩阵完成核心旅程。
- 保存故障注入、恢复、冲突、离线、CJK IME、键盘/屏幕阅读器和安全门禁通过。
- 产物可追溯；macOS 签名/公证和选定 Linux 包的干净环境安装验证通过。

## 3. 当前基线与差距

### 3.1 已观察基线

当前仓库是可启动的 Tauri + React 模板，但与 PRD 目标仍有明显差距：

- `package.json` 只有 React、Tauri API、opener、Vite 和 TypeScript；未声明 Excalidraw SDK、SQLite、文件对话框/文件系统能力、watcher 或测试依赖。
- `src/` 仍是模板界面；没有编辑器适配层、文档状态、标签、工作区或保存调度器。
- `src-tauri/Cargo.toml` 只有 Tauri、opener、Serde 和 JSON；没有 SQLite、异步运行时、文件监听、恢复或错误分类模块。
- `src-tauri/tauri.conf.json` 当前 CSP 为 `null`，构建目标为 `all`；这不代表生产安全配置或平台支持承诺。
- `src-tauri/capabilities/default.json` 只有 `core:default` 和 `opener:default`，尚无受控工作区权限。
- 当前存在基础 Cargo 构建产物，但没有前端测试、Rust 业务测试、桌面 E2E、性能夹具、故障注入、签名、公证或发布流水线。

### 3.2 Phase 0 必须先解决的差距

1. 固定包管理器、依赖锁定和可复现构建入口；Tauri 配置当前使用 `pnpm`，需确认开发环境和 CI 一致。
2. 锁定 Excalidraw SDK 版本并证明离线资源加载路径。
3. 建立 SQLite 迁移、仓储接口和最小故障恢复实验。
4. 建立 Tauri capability、CSP 和 IPC 输入校验的安全基线。
5. 固定至少一个 macOS 和一个 Linux 实验环境，再扩展发布矩阵。

## 4. 目标架构

### 4.1 分层与信任边界

```text
┌──────────────────────────────────────────────────────────┐
│ React UI / Excalidraw Canvas                             │
│ - editor adapter  - tabs  - workspace tree  - status UI  │
└───────────────────────┬──────────────────────────────────┘
                        │ versioned typed IPC
┌───────────────────────▼──────────────────────────────────┐
│ Rust application boundary                                │
│ - command validation  - capability checks  - error codes │
└───────────────┬───────────────────┬──────────────────────┘
                │                   │
        ┌───────▼────────┐  ┌───────▼─────────────────────┐
        │ SQLite hot tier │  │ Filesystem cold tier        │
        │ drafts/recovery │  │ .excalidraw atomic save     │
        │ migrations      │  │ baseline/hash/watch events  │
        └─────────────────┘  └─────────────────────────────┘
```

边界规则：

- React 只持有当前编辑器状态和用户可见状态，不直接调用任意文件系统 API。
- Rust 是路径、权限、JSON Schema、大小上限、版本序号和持久化状态机的权威层。
- SQLite 只保存应用专属草稿、恢复候选、工作区元数据和基线，不替代用户可移植文件。
- 冷层保存由 Rust 执行；前端只有在收到成功响应后才能清除对应脏状态。
- watcher 只能触发重新检查，不能作为“内容已经变化”或“可以安全覆盖”的证明。
- 所有错误使用稳定错误码和用户可操作的建议；禁止把底层错误直接拼接成脚本或 HTML。

### 4.2 预期目录边界

以下是计划目标，不是立即创建的空目录；每个目录随对应垂直切片引入。

```text
src/
├── app/                    # 应用壳、标签、菜单、全局状态
├── editor/                 # ExcalidrawAdapter、编辑器组件、导出、资源加载
├── documents/              # 文档状态、草稿调度、恢复、冲突状态机
├── workspaces/             # 工作区选择、文件树、目录加载
├── ipc/                    # 版本化 Tauri 命令客户端与类型
├── ui/                     # 对话框、错误、状态、焦点和无障碍组件
└── test-fixtures/          # Scene、损坏文件、图片和性能夹具

src-tauri/src/
├── commands/               # IPC 命令入口与参数校验
├── documents/              # JSON 校验、哈希、原子写、基线
├── database/               # SQLite 连接、迁移、仓储与事务
├── recovery/               # session、快照轮换和恢复候选
├── watcher/                # 文件监听、去抖和事件分类
├── workspaces/             # 目录扫描、路径授权、文件索引
├── security/               # capability 边界辅助、路径/输入策略
├── diagnostics/            # 错误码、脱敏日志和诊断导出
└── lib.rs                  # 生命周期、插件注册和命令注册

e2e/                        # 桌面/浏览器可见 E2E 与故障 Harness
tests/                      # 跨层契约、兼容性和性能测试资产
```

### 4.3 SQLite 初始数据模型

SQLite 为第一实现，使用迁移文件管理版本。表结构以最小必要字段开始，具体 SQL 在实现任务中冻结：

| 表 | 用途 | 最低字段/约束 |
| --- | --- | --- |
| `drafts` | 最新热层草稿 | `document_id` 主键、路径标识、Schema 版本、提交序号、Scene JSON、内容哈希、冷层基线哈希、更新时间、脏状态 |
| `recovery_snapshots` | 有限恢复候选 | 文档 ID、序号、快照哈希、Scene/资源、基线哈希、创建时间、应用版本、保留状态 |
| `workspaces` | 活动工作区元数据 | 稳定 ID、显示名、授权根路径、创建/更新时间、状态 |
| `file_baselines` | 已打开文件的外部基线 | 文档 ID、规范路径、内容哈希、大小、mtime、最后检查时间 |
| `schema_migrations` | 数据库迁移记录 | 迁移编号、校验值、应用时间 |

约束：

- 所有文档写入按 `document_id` 串行化；旧提交序号不得覆盖新序号。
- Scene JSON 和恢复内容受大小上限约束，超过上限必须有界拒绝。
- 迁移必须可重复执行，并有升级中断后的恢复或明确回滚行为。
- SQLite 文件放在应用专属数据目录，不放入用户工作区，不随用户文件复制。
- 若需要替换数据库实现，业务层只能依赖仓储接口和版本化领域模型。

### 4.4 文档状态机

```text
unopened
  └─ open ──► clean ── edit ──► dirty
                         │          │
                         │          ├─ hot draft failure ─► unprotected
                         │          ├─ external change ──► conflict
                         │          └─ checkpoint success ─► clean
                         │
                         └─ close/exit ─► saving ─► closed
```

状态约束：

- `clean` 只表示冷层已成功校验并替换，不能仅表示 IPC 请求已发送。
- `dirty` 可同时存在已提交热层；UI 应分别展示“未保存到文件”和“草稿未受保护”。
- `conflict` 禁止自动覆盖，直到用户选择外部版、本地另存、确认覆盖或取消。
- `unprotected` 必须提供重试、另存、导出或诊断路径。
- 关闭窗口时，任何未完成的保存必须有明确的等待、取消或保留草稿行为。

## 5. IPC 契约计划

### 5.1 契约原则

- 所有命令请求和响应带契约版本；不依赖隐式 JSON 字段。
- 前端传递文档 ID、期望基线、提交序号和内容，但 Rust 重新解析、验证和授权。
- 路径只作为受控句柄/规范化结果使用；不把任意路径拼接到 shell 或 HTML。
- 失败响应包含稳定 `code`、用户可见 `messageKey`、是否可重试、是否保留草稿和可选诊断上下文。
- 通过 TypeScript 类型和 Rust Serde 类型生成/维护同一份契约测试；不使用 `any` 绕过校验。

### 5.2 首批命令候选

| 命令 | 方向 | 作用 | 关键失败码 |
| --- | --- | --- | --- |
| `workspace_select` | UI → Rust | 选择并授权工作区根目录 | `permission_denied`、`invalid_workspace` |
| `workspace_list_directory` | UI → Rust | 按需列出授权目录 | `workspace_unavailable`、`path_escape` |
| `document_open` | UI → Rust | 读取并校验标准文件，返回 Scene 与基线 | `not_found`、`invalid_document`、`unsupported_schema` |
| `draft_put` | UI → Rust | 按序写入 SQLite 热层 | `draft_too_large`、`database_busy`、`database_failure` |
| `document_checkpoint` | UI → Rust | 基线校验并执行冷层原子保存 | `external_conflict`、`atomic_replace_failed`、`disk_full` |
| `recovery_list` | UI → Rust | 获取恢复候选摘要 | `recovery_unavailable` |
| `recovery_apply` | UI → Rust | 恢复为副本或经确认覆盖 | `recovery_write_failed`、`stale_baseline` |
| `conflict_resolve` | UI → Rust | 选择外部版、本地另存或确认覆盖 | `conflict_required`、`stale_baseline` |
| `document_export` | UI → Rust/本地适配 | 导出 PNG/SVG | `export_failed`、`target_not_writable` |

Phase 0 只需验证命令边界和错误模型；命令名称和字段在契约测试冻结后才能作为实现接口。

## 6. 分阶段实施路线

### Phase 0：风险验证与基线

目标：证明最高风险假设，冻结最小技术决策。

| ID | 工作项 | 产出 | 退出条件 |
| --- | --- | --- | --- |
| P0-01 | 固定包管理器、锁文件和构建入口 | `package.json`/锁文件/CI 约束记录 | 本地和 CI 使用同一依赖解析方式 |
| P0-02 | 锁定 Excalidraw SDK 候选版本 | 版本 ADR 草案、最小适配器 | macOS 与一个 Linux 环境可加载、编辑、导出同一 Scene |
| P0-03 | 验证离线资源 | 字体/Worker/导出资源清单与断网测试 | 无 CDN 依赖的核心闭环可运行 |
| P0-04 | 建立性能夹具 | 1k/5k/10k 图元、图片和损坏文件夹具 | 记录设备、OS、WebView、SDK、构建模式和样本量 |
| P0-05 | SQLite 最小 PoC | 连接、WAL 候选配置、事务、迁移、强杀恢复报告 | SQLite 能运行草稿写入和读取；失败原因可分类 |
| P0-06 | 原子保存 PoC | 同目录临时文件、校验、替换、故障注入 harness | 支持环境中旧文件或新文件至少一份可解析 |
| P0-07 | 安全边界 PoC | CSP 草案、capability 清单、路径和 JSON 输入策略 | 无全盘权限；越权和畸形输入测试有明确结果 |
| P0-08 | 冻结 Linux 实验矩阵 | 发行版、WebKitGTK、Wayland/X11、架构与 IME 清单 | D-001 记录完成/延期项和已知限制 |

Phase 0 不实现 redb。只有 P0-05 或后续 SQLite 测试出现无法通过门槛的具体问题，才创建 `ADR-DB-002` 评估 redb。

### 8.2 必测故障场景

至少覆盖：

- 临时文件创建、部分写入、同步、重新校验、替换和父目录同步失败。
- SQLite 事务提交失败、数据库锁、迁移中断、应用在状态更新前终止。
- 热层成功但冷层尚未保存时终止，冷层成功但状态清理前终止。
- 保存前、保存中、保存后的外部修改、外部删除和外部重命名。
- watcher 收到自身写入、事件乱序、事件合并、事件丢失或目录卸载。
- 陈旧 session、PID 复用、损坏/超配额恢复候选。
- 无权限、只读文件、磁盘耗尽、Save As 取消、网络完全离线。
- IME composition 中切换标签、撤销、缩放、平移和关闭窗口。

### 8.3 性能夹具与报告

每次报告必须记录：设备型号、CPU 架构、OS 版本、WebView/WebKitGTK 版本、SDK 版本、构建模式、Scene 元素分布、图片大小、样本量和 P50/P95/P99。不得以“平均 60fps”或未经定义的元素数量作为唯一结论。

### 8.4 验证命令与环境策略

当前仓库已有 `package.json` 的 `build`/`dev`/`tauri` 脚本和 Cargo 工程，但完整测试命令尚未建立。Phase 0 需把以下内容写入项目文档和 CI：

- 前端依赖安装、格式化、类型检查、单元测试和生产构建命令。
- Rust 格式化、编译、单元/集成测试和 Clippy 命令。
- Tauri 原生冒烟、桌面 E2E、故障注入和性能基准入口。
- macOS/Linux 的环境版本、依赖、缓存和产物归档方式。

在命令冻结前，不在 README 或发布说明中声称测试流程已经建立。

## 9. SQLite 方案与 redb 触发规则

### 9.1 SQLite 第一实现范围

第一实现只维护 SQLite 路径：

1. 连接生命周期、应用专属数据库位置和 WAL 候选配置。
2. 迁移表、`drafts`、`recovery_snapshots`、`workspaces` 和 `file_baselines`。
3. 单文档顺序提交、事务错误分类和可重试策略。
4. 强杀、锁、磁盘满、迁移中断和数据校验测试。
5. 通过仓储接口隔离业务层，不在前端或业务模块散布 SQL。

SQLite 的 `synchronous`、checkpoint 和忙等待值由基准与故障注入决定；研究文档中的候选值不是默认承诺。

### 9.2 redb 只能在以下条件触发评估

只有出现以下任一情况，才创建并评审 `ADR-DB-002`：

- SQLite 经过一次明确的针对性修复后，仍连续无法满足 NFR-P-005、NFR-R-001、NFR-R-007 或 NFR-R-008。
- SQLite 的已知缺陷导致无法保证草稿顺序、迁移回滚或受支持环境下的数据完整性。
- 经过测量，SQLite 的维护/打包约束成为已批准发布门禁的阻断项。

ADR 必须包含 SQLite 失败证据、redb 对比基准、迁移方案、回滚方案、数据兼容性和新增维护成本。没有这些证据时，不切换数据库。

## 11. 风险与回滚策略

| 风险 | 预防 | 触发后动作 |
| --- | --- | --- |
| SDK API 或离线资源不稳定 | 适配层、锁版本、兼容语料、离线构建检查 | 固定已验证版本，推迟升级；不让业务散布上游 API |
| SQLite 性能/耐久不达标 | 先基准、故障注入和迁移测试；业务依赖仓储接口 | 按 redb 触发规则创建 ADR；未获批准不切换 |
| Linux WebView/IME 差异 | Phase 0 早期实测，记录支持矩阵 | 缩小 Linux 支持范围或推迟平台门禁，不伪称全 Linux 支持 |
| 原子替换在某类文件系统不可靠 | 保存前能力分类、草稿保留和限制提示 | 标记尽力/不支持；要求另存到受支持位置 |
| 全量 Scene 序列化卡顿 | 防抖、仪表化、性能夹具 | 先降频/限额；仅经 ADR 引入 Worker/增量协议 |
| 失败状态导致假“已保存” | 状态机、Rust 权威响应、故障注入 | 阻断发布，回滚到上一个已验证保存路径 |
| 权限/路径越权 | Rust 规范化、授权根校验、TOCTOU 测试 | 禁止发布；撤销新增 capability，补安全测试 |

代码回滚必须保留用户已有 SQLite 数据和冷层文件；任何 Schema 变更先提供迁移回滚/备份策略，不使用破坏性重置数据库的方式修复开发问题。
