# ADR-007 全树 WebKit 基线重校准 RSS/idle-CPU，并修正 pan 与静置写盘 workload

**状态**：Accepted

**日期**：2026-08-15

## 背景/Context

ADR-004 规定绝对预算不得静默抬高，任何分代必须先有测量证据再写 ADR。下文用活动名称，不用「Phase N」：`tasks.md` 的 Phase 1–10 是 SDD 开发阶段（Setup / Foundational / US1–US7 / Polish）；2026-08-14 本地交接里曾用同一词指测量尺子修复、归因和预算校准，二者不是同一套编号。

2026-08-14/15 **全树口径重测**把 RSS 从 Tauri 主进程改为全进程树（含 reparent 到 launchd 的 WebContent/GPU/Networking）后，参考 VM 与物理机都显示空闲约 411 MB、10k 约 730 MB，旧的 150 MB / 350 MB 全树预算从一开始就不可达。同日 **物理机归因**进一步说明：

- 空闲 400.7 MB = WebContent 195.4 + Tauri 147.9 + GPU 40.4 + Network 17.0；10k 加载后 761.7 MB，增量主要在 WebContent（+232 MB）与 Tauri（+92 MB）。
- 空画布可见窗口、harness 禁用 App Nap 时 CPU P95 已是 9.4%；15 分钟 soak 后静置物理机 16.3%、参考 VM 28.9%。1% 对照的是可休眠后台，不是当前测量条件。
- 官方 pan/zoom 每帧 `updateScene({appState})` 振荡 zoom ±15%，物理机 24.38 fps；同场景锁定 zoom=1 只平移为 59.69 fps。22 fps 是测试视口，不是 10k 平移本身。
- soak 结束后立刻观察的 8 次写盘是一次 `save_draft` recovery 原子写加一次 3 秒 idle checkpoint，再等 5 秒后 20 秒窗口为 0。零持续写入预算量的是刷新之后的静默，不是崩溃安全刷新本身。

冷启动 2 s、soak RSS 增长（≤50 MB 且 ≤15%）、编辑期写合并比、冻结 100 ms 本 ADR 不改。

## 决策/Decision

**预算重校准**（P95，十进制 MB = 10^6 bytes，与既有 `PERF_BUDGETS` 惯例一致）：

| 预算 | 旧值 | 新值 | 依据 |
|------|------|------|------|
| 空载全树 RSS | 150 MB | **500 MB** | 本应用实测 ~411 MB，约 20% 余量；2026-08-16 空载对照见下，411 MB 落在空 Tauri 壳与 Safari+Excalidraw 之间 |
| 10k 场景稳定后全树 RSS | 350 MB | **950 MB** | 实测加载后 ~762 MB，约 25% 余量（非空载对照） |
| 静置 CPU P95 | 单逻辑核 1% | **单逻辑核 35%** | 参考 VM soak 后 28.9%，约 20% 余量；物理机同窗口约 16%，差额记为虚拟化，不另设物理门槛 |

**workload 修正**（不改产品平移或 checkpoint 实现）：

- T090 10k「平移/缩放」脚本改为**恒定 zoom=1 的平移**。SC-005 的 30 fps 门禁衡量用户式平移，不再每帧振荡缩放。连续 pinch-zoom 10k 不是本门禁。
- T108 静置 60 秒写盘观察在脚本编辑结束后先等待 **5 秒**（覆盖 `DraftScheduler` debounce 300 ms + idle checkpoint 3 s 及余量），再开始 60 秒窗口。预算仍是该窗口内零持续写入。

本决策同步：宪法原则 IV（v3.3.0）、ADR-004 修订注记、私有 specs（SC-002/005/013、plan.md、tasks.md T090/T108、research.md R18）、`PERF_BUDGETS`、`applyPerformanceViewport`、`edit-soak.spec.ts`。

预算与 pan 脚本变化构成新的测量序列；不得与 2026-08-13 Tauri-only 或 2026-08-14/15 振荡-zoom / 立即观察写盘的报告直接比较绝对值。

## 空载对照（2026-08-16）

500 MB 的校准源仍是本应用 2026-08-14/15 全树口径重测与物理机归因，不是下面两行。对照只回答「411 MB 全树空闲是不是测量口径或壳层泄漏」：同一套 launchd-reparent 全树归因，物理机热身 30 s 再采样 60 s。原始 JSON 提交在 `docs/evidence/`（harness 的 `e2e/perf/results/` 被 gitignore，一次性对照不能只放 `/tmp`）。

| 场景 | 全树 RSS P95 | host | WebContent | GPU | Network |
|------|----------------|------|------------|-----|---------|
| 空白 Tauri v2 窗口（无插件、空白 HTML） | **201.2 MB** | 118.9 | 37.1 | 28.2 | 17.0 |
| 本应用空闲（`startup-idle.host` 全树 / 物理机归因分角色） | **411.0 MB**（分角色 400.7） | 147.9 | 195.4 | 40.4 | 17.0 |
| Safari 新进程打开空的 [excalidraw.com](https://excalidraw.com/) | **629.4 MB** | 233.2 | 299.8 | 47.9 | 48.7 |

本应用落在空壳与 Safari+Excalidraw 之间；WebContent 195 MB 低于 Safari 加载同一画布的 300 MB。500 MB 对照的是 WKWebView 加载 Excalidraw 的基线，不是把 411 MB 算进自己的代码。报告：[`idle-control-tauri.json`](../evidence/idle-control-tauri.json)（SHA-256 `09fbc287…`）、[`idle-control-safari.json`](../evidence/idle-control-safari.json)（SHA-256 `ad06765c…`）。

10k 的 950 MB 与 idle CPU 的 35% **不是**这次对照产生的。对照在未禁用 App Nap 时 idle CPU P95 ≈ 0%，不能用来否定 harness（可见窗口 + 禁用 App Nap）下的 9–29%。

## 后果/Consequences

**积极**：

- 全树 RSS 与可见窗口 idle CPU 的 `pass`/`fail` 对照的是 WKWebView 桌面应用的真实基线，而不是主进程假象。
- pan 门禁与用户平移同量级；静置写盘门禁不再把设计内的 idle checkpoint 算成泄漏。

**消极**：

- 500 / 950 MB 与 35% CPU 比原预算松一个数量级。它们捕获的是相对该基线的回归，不再假装空画布能进 150 MB。
- 参考 VM idle CPU 仍可能因虚拟化高于物理机；35% 按 VM 取证校准，物理机更严的体感不自动成为第二套硬门槛。
- soak RSS 增长与冷启动未在本 ADR 重校准，T108/T090 仍可能在这些项上 `fail`。2026-08-16 分角色归因与「保持这两条预算不变」见 [ADR-008](./ADR-008.md)。

## 备选方案/Alternatives

- **保持 150 / 350 MB 与 1% CPU**：口径诚实后永久 `fail`，失去回归信号，被否。
- **按物理机 16% 校准 idle CPU**：参考环境是 VM（ADR-004），VM 28.9% 仍会失败，被否。
- **从产品侧拆掉 idle checkpoint 或压 WebKit RSS**：物理机归因证明前者是崩溃安全、后者主要是 WebContent 基线；不作为本 ADR 的代码范围，被否。
- **把振荡 zoom 留作 10k 门禁**：测的是每帧重光栅，不是平移可用性，被否。
