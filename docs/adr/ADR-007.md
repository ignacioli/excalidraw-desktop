# ADR-007 全树 WebKit 基线重校准 RSS/idle-CPU，并修正 pan 与静置写盘 workload

**状态**：Accepted

**日期**：2026-08-15

## 背景/Context

ADR-004 规定绝对预算不得静默抬高，任何分代必须先有测量证据再写 ADR。Phase 1 把 RSS 口径从 Tauri 主进程改为全进程树（含 reparent 到 launchd 的 WebContent/GPU/Networking）后，参考 VM 与物理机都显示空闲约 411 MB、10k 约 730 MB，旧的 150 MB / 350 MB 全树预算从一开始就不可达。Phase 2 物理机归因进一步说明：

- 空闲 400.7 MB = WebContent 195.4 + Tauri 147.9 + GPU 40.4 + Network 17.0；10k 加载后 761.7 MB，增量主要在 WebContent（+232 MB）与 Tauri（+92 MB）。
- 空画布可见窗口、harness 禁用 App Nap 时 CPU P95 已是 9.4%；15 分钟 soak 后静置物理机 16.3%、参考 VM 28.9%。1% 对照的是可休眠后台，不是当前测量条件。
- 官方 pan/zoom 每帧 `updateScene({appState})` 振荡 zoom ±15%，物理机 24.38 fps；同场景锁定 zoom=1 只平移为 59.69 fps。22 fps 是测试视口，不是 10k 平移本身。
- soak 结束后立刻观察的 8 次写盘是一次 `save_draft` recovery 原子写加一次 3 秒 idle checkpoint，再等 5 秒后 20 秒窗口为 0。零持续写入预算量的是刷新之后的静默，不是崩溃安全刷新本身。

冷启动 2 s、soak RSS 增长（≤50 MB 且 ≤15%）、编辑期写合并比、冻结 100 ms 本 ADR 不改。

## 决策/Decision

**预算重校准**（P95，十进制 MB = 10^6 bytes，与既有 `PERF_BUDGETS` 惯例一致）：

| 预算 | 旧值 | 新值 | 依据 |
|------|------|------|------|
| 空载全树 RSS | 150 MB | **500 MB** | 实测 ~411 MB，约 20% 余量 |
| 10k 场景稳定后全树 RSS | 350 MB | **950 MB** | 实测加载后 ~762 MB，约 25% 余量 |
| 静置 CPU P95 | 单逻辑核 1% | **单逻辑核 35%** | 参考 VM soak 后 28.9%，约 20% 余量；物理机同窗口约 16%，差额记为虚拟化，不另设物理门槛 |

**workload 修正**（不改产品平移或 checkpoint 实现）：

- T090 10k「平移/缩放」脚本改为**恒定 zoom=1 的平移**。SC-005 的 30 fps 门禁衡量用户式平移，不再每帧振荡缩放。连续 pinch-zoom 10k 不是本门禁。
- T108 静置 60 秒写盘观察在脚本编辑结束后先等待 **5 秒**（覆盖 `DraftScheduler` debounce 300 ms + idle checkpoint 3 s 及余量），再开始 60 秒窗口。预算仍是该窗口内零持续写入。

本决策同步：宪法原则 IV（v3.3.0）、ADR-004 修订注记、私有 specs（SC-002/005/013、plan.md、tasks.md T090/T108、research.md R18）、`PERF_BUDGETS`、`applyPerformanceViewport`、`edit-soak.spec.ts`。

预算与 pan 脚本变化构成新的测量序列；不得与 2026-08-13 Tauri-only 或 2026-08-14/15 振荡-zoom / 立即观察写盘的报告直接比较绝对值。

## 后果/Consequences

**积极**：

- 全树 RSS 与可见窗口 idle CPU 的 `pass`/`fail` 对照的是 WKWebView 桌面应用的真实基线，而不是主进程假象。
- pan 门禁与用户平移同量级；静置写盘门禁不再把设计内的 idle checkpoint 算成泄漏。

**消极**：

- 500 / 950 MB 与 35% CPU 比原预算松一个数量级。它们捕获的是相对该基线的回归，不再假装空画布能进 150 MB。
- 参考 VM idle CPU 仍可能因虚拟化高于物理机；35% 按 VM 取证校准，物理机更严的体感不自动成为第二套硬门槛。
- soak RSS 增长与冷启动未在本 ADR 重校准，T108/T090 仍可能在这些项上 `fail`。

## 备选方案/Alternatives

- **保持 150 / 350 MB 与 1% CPU**：口径诚实后永久 `fail`，失去回归信号，被否。
- **按物理机 16% 校准 idle CPU**：参考环境是 VM（ADR-004），VM 28.9% 仍会失败，被否。
- **从产品侧拆掉 idle checkpoint 或压 WebKit RSS**：Phase 2 证明前者是崩溃安全、后者主要是 WebContent 基线；不作为本 ADR 的代码范围，被否。
- **把振荡 zoom 留作 10k 门禁**：测的是每帧重光栅，不是平移可用性，被否。
