## 判定与绑定规则

- `PASS` 只表示该行指定的事实与证据层已通过；不能传递给其他行。`FAIL` 表示实际执行后行为或预算不符；保留原始失败与后续修复记录。必需报告、身份、环境或人工决定缺失时记 `BLOCKED`；尚未进入该检查的工作记 `PENDING`。同一事实可在不同层分别有 `PASS` 和 `BLOCKED`。
- 每份原始报告应记录产品完整提交、二进制种类与 SHA-256、生产 `.app` 的 bundle ID/版本/包哈希（适用时）、系统版本/build/架构、文件系统类型与隔离根、fixture/seed、document/request/operation/version ID、操作前后文件及场景哈希、图片/对象哈希及引用检查、故障阶段、子进程退出码或信号、fresh-process 结果、执行命令、时间和 verdict。未采集的字段写“未记录”，不能从源码或后续另一包补推。
- `SIGKILL` 证明被测进程在指定屏障和该测试文件系统上的中断与重启判定；不证明物理断电、设备缓存刷新或 APFS power-loss durability。受控 `ENOSPC`/`EACCES` 注入也不等于物理磁盘耗尽或真实权限环境。
- 下表的 `owner` 是主要证据负责人；补充测试只能为另一事实提供上下文。精确生产包必须与待验产品提交重新绑定。旧包的菜单、视觉或性能结果不能继承给新提交。
